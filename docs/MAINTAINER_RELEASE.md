# 维护者发布流程

## 版本编号

Cargo/npm/Tauri、运行显示、标签和更新文件使用一致的三段版本号。当前准备发布 `2.5.0`，标签为 `v2.5.0`；常规小版本按 `2.x.0` 递增。

## 2.5.0 R3：已批准的发布范围

用户已确认并批准上传 R3，仅提供高光时刻。WTF、剧情和录像分析仍未正式提供；中央 `module-catalog.json` 三项 `released` 均为 `false`，前后端门禁都要保留。官方状态开放后还须检测到兼容安装才能启动，不因本机有模块而绕过。

本次用户附件仅包含主高光程序及配套工具、说明，不包含 WTF 或其他模块 EXE、`module.json`。R2 双 EXE 仅为内部预览，候选、旧程序和用户数据保留。确认目录状态、包内容和发布文案一致，不把开发完成写成模块正式提供。

R3 已记录 213 项 Rust 通过、9 项外部条件测试 ignored，86 项前端测试、格式、严格 Clippy 和前端生产构建通过。R3 没有另跑真实 DEM，也没有新的 UI、鼠标、保存窗口或游戏实测。用户批准上传不改变这些验证边界，不将 R1/R2 结果记作新实测。

## 源码门禁

```powershell
.\scripts\verify.ps1
```

确认 Git 中不存在 DEM、媒体、任务缓存、二进制、真实比赛编号、玩家标识、本机绝对路径、密钥或内部规划记录。公开仓库必须继续保留根目录许可证、品牌规则和第三方声明。

最终源码和文档先审查、提交，再构建签名候选。`desktop-release.ps1` 要求干净工作区并把当前提交写入候选清单；不得将旧提交的安装包、签名或 R3 预览 EXE 的哈希冒充最终附件。构建使用 `CARGO_TARGET_DIR` 时，必须从实际输出目录取新工件，避免误取旧 `target/` 文件。

## 签名候选

正式安装包使用被 Git 忽略的 `tools\ffmpeg\bin\` 和 `.release-secrets\`。签名目录包含私钥、公钥与当前 Windows 用户可解密的密码文件，不得复制到候选目录或 Git。

```powershell
.\scripts\desktop-release.ps1
```

隔离工作树可以显式引用维护者主工作树的签名目录：

```powershell
.\scripts\desktop-release.ps1 -SigningRootOverride "[PROJECT_ROOT]\.release-secrets"
```

脚本先执行完整验证，再生成 `release\candidate\<版本>\`，其中包括便携版、安装包、更新安装包、签名、`latest.json` 和绑定源码提交的候选清单。候选不会自动覆盖根目录正式版。

运行前核对同版本候选目录：现有脚本会清除并重建 `release/candidate/<版本>`，其中有独有资料时须先保全，不得删除 R2/R3 历史预览。签名材料只由发布脚本使用，不输出内容，不复制到 Git、候选或附件。安装包形成后重新核对本次工件的版本、GUI 子系统、SHA-256、签名和仅高光范围。

## 正式提升

候选的适用验证、已执行与未执行边界记录完整后，确认 `main`、`v<版本>` 标签和候选清单指向同一提交。需要提升本机入口时执行：

```powershell
.\scripts\promote-release.ps1 -Version <版本> -ConfirmPromotion
```

提升脚本会再次验证哈希与源码，把上一版 EXE 保存到 `release\history\`，再原子替换根目录启动文件和正式安装包。

本机入口提升与 GitHub 发布是两项动作，按本轮授权执行，不因发布标签而自动清理用户任务或内部候选。当前仅高光的发布批准已取得，不再把“待用户确认”作为上传阻断项。

## GitHub Release

GitHub Actions 只验证源码，不持有更新签名私钥，也不重建已经验收的安装包。维护者在推送前必须再次确认官方仓库、`main`、标签和以下附件：

- `latest.json`
- `luckcaty-cut-dota2_<版本>_x64-setup.exe`
- `luckcaty-cut-dota2_<版本>_x64-setup.exe.sig`
- 可选的便携版与面向用户的安装包

Release 说明包含功能变化、SHA-256、FFmpeg 许可证与来源链接，不把静态作者信息写成更新项。

2.5.0 正文采用 `CHANGELOG.md` 的对应版本节，签名脚本也从该节提取更新说明。正式 Release 创建前，补入本次最终安装包与可选便携版的 SHA-256；不填未生成工件的猜测值，不复用 R1/R2 哈希。正文必须说明仅高光、三模块未提供、排查 ZIP 和固定超时未改。

推送源码或创建标签不等于完成 Release。发布后只读核对官方标签、附件名称与大小、最终哈希、签名和 `latest.json` 的版本及下载地址，再将 README、更新记录和当前状态改为已上线。线上成功前保持“用户已确认、待发布”，不提前宣称已发布。

客户端更新策略固定为只检查和提示；用户点击后才下载、验签与安装，分析或导出期间禁止安装。只有著作权人或持有明确书面授权的发布者可以对外发布安装包。

## 缓存失效边界

渲染器的 `CAPTURE_PIPELINE_VERSION` 参与片段缓存指纹。修改 Dota 2 HUD、镜头、
`startmovie/endmovie` 或帧/音频编码行为时必须同步升级该值，并运行缓存指纹回归测试；
纯 UI 或文案调整不需要清空片段缓存。
